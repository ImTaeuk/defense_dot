CardChoiceApplier 구조 결정 — 구 동기 Apply 를 남길까 없앨까

결정 제안서 선택 대기 이펙트 풀링 마이그레이션 Task 4-C · 2026-07-04

1. 결정 요지 — 무엇을 고르는가

Task 4-C 는 카드 획득 시 이펙트를 미리 예열(warmup) 하도록 배선하는 작업입니다. 예열은 await pool.WarmupAsync(...) 라는 비동기 호출이고, await 는 반드시 async 메서드 안에서만 쓸 수 있습니다. 따라서 비동기 진입점 ApplyAsync 가 새로 생기는 것은 이미 확정입니다.

이 보고서가 묻는 것은 딱 하나입니다 — 기존의 동기 Apply 를 그대로 남길 것인가, 아니면 지우고 ApplyAsync 하나로 통일할 것인가.

핵심 한 줄: 걸림돌은 EditMode 테스트 4개가 동기 Apply 를 직접 호출한다는 점 — 지우면 이 테스트 4개를 UniTask 대기 형태로 뜯어고쳐야 한다.

2. 현재 동작 (지금의 호출 구조)

  1. 레벨업 → CardSelectionPresenter.cs:60 HandleSelected(idx) 가 카드 확정을 수신 (반환형 void, 이벤트 핸들러)
  2. CardSelectionPresenter.cs:63 에서 CardChoiceApplier.Apply(core, current[idx]) 동기 호출
  3. CardChoiceApplier.cs:9 Apply() 가 신규 추가 또는 목표 레벨까지 레벨업 (풀·예열 개념 없음)
  4. 같은 로직을 CardChoiceApplierTests.cs:54, 66, 79, 91 4개 테스트가 Apply(core, choice) 로 직접 검증 (풀 없이 추가·레벨업 계산만)
즉 Apply 는 런타임 호출부 1곳 + 테스트 4곳, 총 5곳에서 쓰입니다. 런타임 1곳은 어차피 ApplyAsync 로 바뀌지만, 테스트 4곳이 이 결정의 실질 비용입니다.

3. 제약의 근본 원인 — 왜 테스트가 걸림돌인가

Assets/Tests/EditMode/CardChoiceApplierTests.cs · L51-92 (발췌)
[Test]   // ← NUnit 동기 테스트. async 아님
public void NewCard_AddsAndLevelsUp()
{
    var core = new StubCore();
    CardChoice choice = CardChoice.NewCard(Active(), CardTier.New, toLevel: 3);

    CardChoiceApplier.Apply(core, choice);   // 동기 호출 — 4개 테스트 공통

    Assert.AreEqual(1, core.added, "신규 추가 1회");
    Assert.AreEqual(2, core.leveled, "레벨 1 → 3 이면 레벨업 2회");
}

이 테스트들은 StubCore 로 순수 계산 로직(추가/레벨업 횟수) 만 검증합니다. 풀이나 예열과는 무관합니다. 그런데 동기 Apply 를 없애면 이 4개가 UniTask 를 반환하는 ApplyAsync 를 호출해야 하고, NUnit [Test] 는 동기라 .GetAwaiter().GetResult() 같은 군더더기를 매번 붙여야 합니다. 검증 대상(계산 로직)은 그대로인데 테스트 표현만 지저분해지는 것이 문제의 본질입니다.

4. 이미 확정된 사항

  • 예열 타이밍 — "예열 완료 후 능력추가·창닫기" 선택 확정. pauseOnCardSelect 로 timeScale=0 정지 상태이므로 예열 몇 프레임 대기가 게임 흐름을 끊지 않음. 순서는 예열 → AddAbility → Hide → ShowNext.
  • 예열은 New 카드에서만 — 레벨업 카드는 이미 보유한 능력이므로 예열 불필요(코어가 ContainsKey 로 no-op 스킵).
  • 비동기 진입점 ApplyAsync 신설은 확정 — 이 보고서 밖의 사안.

5. 설계 원칙 — 프로젝트 컨벤션 정렬

"동기 로직은 그대로 두고 비동기가 그것을 얇게 감싼다"는 구조가 이 코드베이스에 이미 두 군데 자리잡고 있습니다. 선택지 A(유지+래핑)는 이 기존 사상과 정확히 같은 결을 따릅니다.

레퍼런스위치차용 포인트
PoolManager PoolManager.cs:34 WarmupAsync / L58 Get<T> 준비는 비동기, 사용은 동기 — 목적별로 진입점을 나란히 공개. 없애서 하나로 합치지 않음
CoreAbilitySystem (이번 Task 4-B 형제 작업) CoreAbilitySystem.cs:31 Setup + 신설 WarmupAndEquipAsync 동기 구성 로직을 async 가 감쌈 — Setup(동기) 유지, 예열+장착만 async 진입점으로 추가
결합 결론: 이 프로젝트는 "비동기 껍질이 검증된 동기 알맹이를 감싼다"를 이미 표준으로 쓴다. ApplyAsync 가 Apply 를 감싸는 선택지 A 는 새 패턴이 아니라 기존 패턴의 반복이다.

레퍼런스 ① PoolManager — 준비(async)와 사용(sync)의 분리

Assets/Scripts/Core/Pooling/PoolManager.cs · L34, L58
// 준비: 비동기 (로드·프리웜)

두 진입점을 합치지 않고 목적별로 공개한다. 호출자는 준비가 끝난 뒤 동기 Get 을 부른다 — ApplyAsync(준비) + Apply(사용/계산)의 관계와 동형이다.

    public static void Apply(ICardCommandTarget core, CardChoice choice)

        else { ... 레벨업 ... }

    public static async UniTask ApplyAsync(
