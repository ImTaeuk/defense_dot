UIRoot 자동 배선 설계 — 예제로 보는 설명

설계 예제 협의 중 중앙 팩토리(자동화) 방향 · 2026-06-30
한 줄 요약: UIRoot 는 List<UIView> 와 팩토리만 들고, 새 UI 를 추가해도 UIRoot·팩토리·GameManager 코드는 손대지 않는다. View 가 제네릭으로 자기 Presenter 타입만 선언하고, 팩토리가 리플렉션으로 생성한다.

1. 지금 문제 — UIRoot 가 모든 걸 안다

현재 UIRoot.cs 는 View 마다 개별 SerializeField 를 들고, Inject 에서 타입별로 직접 new XxxPresenter(...) 합니다. 새 UI 를 하나 추가할 때마다 필드 1개 + 분기 1블록이 늘고, Arena 에서 안 쓰는 buildModalView·towerRoster 같은 빈 슬롯이 남습니다.

Assets/Scripts/UI/InGame/UIRoot.cs (현재)
[SerializeField] private ArenaHudView arenaHud;
[SerializeField] private TowerBuildModalView buildModalView;   // Arena 에선 빈 슬롯
[SerializeField] private TowerRoster towerRoster;              // Arena 에선 빈 슬롯
[SerializeField] private GameResultView gameResultView;
[SerializeField] private CardSelectionView cardSelectionView;

public void Inject(in HudContext ctx, GameFlowModel flow, ...)
{
    if (arenaHud != null) presenters.Add(new ArenaHudPresenter(arenaHud, ctx.Economy, ...));   // 타입마다 분기
    if (gameResultView != null) presenters.Add(new GameResultPresenter(gameResultView, flow));
    if (cardSelectionView != null) presenters.Add(new CardSelectionPresenter(...));
    // 새 UI = 필드 추가 + 여기 분기 추가 …계속 성장
}

2. 설계 — 4개 부품

부품역할핵심
UIView<TPresenter>View 가 자기 Presenter 타입만 선언제네릭 1줄
UIContextUI 합성 재료(모델·설정) 묶음 (Parameter Object)readonly struct
UIPresenterFactoryUIView → IPresenter 생성 (리플렉션)POCO, switch 없음
UIRootList<UIView> 순회 → 생성·Initialize타입 모름
흐름: GameManager 가 UIContext 와 팩토리를 만들어 UIRoot.Inject(factory) → UIRoot 는 리스트의 각 UIView 를 팩토리에 넘겨 Presenter 를 받고 Initialize.

3. 부품별 예제 코드

① UIView<TPresenter> — View 가 Presenter 타입만 선언

Assets/Scripts/UI/Base/UIView.cs (확장)
// 비제네릭 베이스 — UIRoot 는 이 타입으로만 리스트를 든다
public abstract class UIView : UIObject, IUIShowable
{
    public abstract System.Type PresenterType { get; }   // 팩토리가 읽음
    // Show / Hide / OnShown / OnShow / OnHide …
}

// 제네릭 — 각 View 가 자기 Presenter 타입을 한 줄로 선언
public abstract class UIView<TPresenter> : UIView where TPresenter : IPresenter
{
    public sealed override System.Type PresenterType => typeof(TPresenter);
}

이렇게 두면 View 는 Presenter 의 타입만 알 뿐, 어떻게 생성되는지·무슨 의존성이 필요한지는 모릅니다.

② UIContext — 의존성 묶음 (Parameter Object)

Assets/Scripts/UI/UIContext.cs (신규)
public readonly struct UIContext
{
    public readonly EconomyModel Economy;
    public readonly CoreModel Core;
    public readonly WaveModel Wave;
    public readonly ScoreModel Score;
    public readonly RoundTimerModel Timer;
    public readonly GameFlowModel Flow;
    public readonly LevelModel Level;
    public readonly int EnemyCapacity;
    public readonly TowerPlacementController Placement;
    public readonly TowerRoster Roster;
    // … CardConfig, AbilityPool, CoreTarget 등 UI 합성에 필요한 재료

    public UIContext(EconomyModel economy, CoreModel core, /* … */)
    { Economy = economy; Core = core; /* … */ }
}
새 의존성이 생기면 여기 한 곳만 늘어납니다. UIRoot·팩토리는 무관.

③ View 와 Presenter — 선언 + 생성자에서 추출

Assets/Scripts/UI/Views/ArenaHudView.cs
public sealed class ArenaHudView : UIView<ArenaHudPresenter>   // ← 타입 선언 끝
{
    [SerializeField] private GoldWidget goldWidget;
    [SerializeField] private ScoreWidget scoreWidget;
    // … ApplyGold / ApplyScore / ApplyRound / ApplyTime / ApplyEnemies
}
Assets/Scripts/UI/Presenters/ArenaHudPresenter.cs
public sealed class ArenaHudPresenter : UIPresenter<ArenaHudView>
{
    private readonly EconomyModel economy;
    private readonly ScoreModel score;
    private readonly WaveModel wave;
    private readonly RoundTimerModel timer;
    private readonly int enemyCapacity;

    public ArenaHudPresenter(ArenaHudView view, UIContext ctx) : base(view)
    {
        economy = ctx.Economy;  score = ctx.Score;   // 필요한 것만 추출, ctx 는 버림
        wave = ctx.Wave;  timer = ctx.Timer;  enemyCapacity = ctx.EnemyCapacity;
    }

    protected override void OnInitialize()
    {
        Bind(economy.Gold, view.ApplyGold);
        Bind(score.Score,  view.ApplyScore);
        // … wave.Progress / timer.Time / wave.RemainingEnemies
    }
}
핵심: 생성자에서 ctx 의 필요한 것만 꺼내 구체 필드로 저장하고 ctx 는 보관하지 않습니다. → 의존성이 생성자에 명시적으로 드러남(서비스 로케이터가 아니라 Parameter Object).

④ UIPresenterFactory — switch 없는 자동 생성

Assets/Scripts/UI/UIPresenterFactory.cs (신규 · POCO)
public sealed class UIPresenterFactory
{
    private readonly UIContext context;

    public UIPresenterFactory(UIContext context) { this.context = context; }

    public IPresenter Create(UIView view)
    {
        if (view == null) return null;
        return (IPresenter)System.Activator.CreateInstance(
            view.PresenterType, view, context);   // (TView, UIContext) 생성자 호출
    }
}

분기(switch)가 없습니다. View 종류가 10개든 50개든 이 코드는 그대로입니다.

⑤ UIRoot — 리스트만 순회

Assets/Scripts/UI/InGame/UIRoot.cs
public sealed class UIRoot : MonoBehaviour
{
    [SerializeField] private List<UIView> views = new List<UIView>();   // 필드는 이것 하나
    private readonly List<IPresenter> presenters = new List<IPresenter>();

    public void Inject(UIPresenterFactory factory)
    {
        foreach (UIView view in views)
        {
            IPresenter presenter = factory.Create(view);
            if (presenter == null) continue;
            presenters.Add(presenter);
            presenter.Initialize();
        }
    }

    private void OnDestroy()
    {
        foreach (IPresenter presenter in presenters) presenter.Dispose();
        presenters.Clear();
    }
}

4. 새 UI 를 추가해 보면 (상점 패널 예)

"개발하며 추가/삭제를 얼마나 더 할지 모른다"는 우려가 바로 이 부분입니다. 자동화에서는 새 클래스 2개만 만들면 끝입니다.

Assets/Scripts/UI/Views/ShopView.cs + Presenters/ShopPresenter.cs (신규)
public sealed class ShopView : UIView<ShopPresenter>   // ① 타입 선언
{
    [SerializeField] private TextMeshProUGUI goldText;
    public void ApplyGold(int gold) => goldText.text = gold.ToString();
}

public sealed class ShopPresenter : UIPresenter<ShopView>   // ② (View, UIContext) 생성자
{
    private readonly EconomyModel economy;
    public ShopPresenter(ShopView view, UIContext ctx) : base(view) { economy = ctx.Economy; }
    protected override void OnInitialize() => Bind(economy.Gold, view.ApplyGold);
}

그리고 씬에서 UIRoot 의 views 리스트에 ShopView 를 드래그하면 끝입니다.

파일새 UI 추가 시
UIPresenterFactory.cs수정 0
UIRoot.cs수정 0
GameManager.cs수정 0 (ShopPresenter 가 쓰는 모델이 이미 UIContext 에 있으면)
UIContext.cs새 의존성이 필요할 때만 필드 1개 추가

5. Before / After — UIRoot

Assets/Scripts/UI/InGame/UIRoot.cs
▼ BEFORE — 타입마다 필드 + 분기 (새 UI 마다 성장)
[SerializeField] private ArenaHudView arenaHud;
[SerializeField] private TowerBuildModalView buildModalView;
[SerializeField] private TowerRoster towerRoster;
[SerializeField] private GameResultView gameResultView;
[SerializeField] private CardSelectionView cardSelectionView;

public void Inject(in HudContext ctx, GameFlowModel flow, ...)
{
    if (arenaHud != null) presenters.Add(new ArenaHudPresenter(arenaHud, ctx.Economy, ...));
    if (gameResultView != null) presenters.Add(new GameResultPresenter(gameResultView, flow));
    if (cardSelectionView != null) presenters.Add(new CardSelectionPresenter(...));
}
▼ AFTER — 리스트 하나 + 순회 (새 UI 에도 불변)
[SerializeField] private List<UIView> views = new List<UIView>();

public void Inject(UIPresenterFactory factory)
{
    foreach (UIView view in views)
    {
        IPresenter p = factory.Create(view);
        if (p == null) continue;
        presenters.Add(p); p.Initialize();
    }
}
미사용 필드(buildModalView·towerRoster) 문제도 자동 소멸 — 씬마다 그 씬에 있는 View 만 리스트에 담으면 됩니다.

6. 이득과 대가 (정직하게)

측면자동화 결과
새 UI 추가View+Presenter 1쌍 + 리스트 드래그. 배선 코드 무수정
미사용 필드소멸 (씬별 리스트)
의존성 명시성생성자에서 ctx 추출 → 유지 (로케이터 아님)
테스트팩토리·Presenter 모두 POCO → EditMode 격리 테스트 가능
View → Presenter 결합제네릭으로 타입 의존이 생김 (생성/의존성은 여전히 모름)
타입 안전성Activator 리플렉션 — (TView, UIContext) 생성자 없으면 런타임 에러. 생성 1회라 초기화 때 즉시 드러나고 테스트로 커버
UIContext의존성 묶음 → 새 의존성 시 여기 확장 (god object 화 주의, 단 Presenter 는 자기 것만 추출)
