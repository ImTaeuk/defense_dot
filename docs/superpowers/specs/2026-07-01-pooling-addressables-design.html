공용 풀링 시스템 & Addressables 인프라 — 설계 · 핸드오프

설계 제안서 구현 대기 · 메인 세션 인계 분석 완료 · 2026-07-01

1. 제보 요지

사용자 제보: "현재 피격 이펙트가 전혀 안 보인다. 피격 이펙트가 작아서 안 보이는 것 같은데?"

가설(작아서 안 보임)을 검증하는 과정에서 의존 체인이 드러나, 단순 이펙트 수정이 공용 풀링 + Addressables 인프라라는 선행 작업으로 확장됐다. 스케일이 커서 "하나씩" 분해해 메인 세션에서 의존 순서대로 처리한다.

핵심: 피격 VFX 는 존재·동작하나(크기·배경 때문에 안 보임), 그 재생 경로가 매번 Instantiate/Destroy 라 풀링이 필요하고, 풀이 프리팹을 약하게 참조하려면 Addressables 가 선행이다.

2. 현재 동작 (재현 경로)

  1. 타워 능력이 투사체 발사 → 투사체가 적에 명중
  2. ProjectileEffect.cs:67 가 명중 시 VfxPlayer.SpawnOneShot(hitVfxPrefab, ...) 호출
  3. VfxPlayer.cs:75 가 Instantiate 후 파티클 수명 뒤 Destroy (일회성, 풀링 없음)
  4. Hit_Water 파티클이 적 위치에 재생되나, 적(≈589배) 대비 scale 1 이라 작고 밝은 배경에 묻혀 시각적으로 안 보임 (TASK-014 B-3 기지 이슈)

3. 근본 원인

Assets/Scripts/Systems/Abilities/Effects/VfxPlayer.cs · SpawnOneShot() L75
// 일회성 연출 스폰 — 재생 후 실제 길이만큼 뒤 파괴
public static VfxPlayer SpawnOneShot(GameObject prefab, Vector3 pos, Quaternion rot)
{
    if (prefab == null) return null;
    GameObject go = Instantiate(prefab, pos, rot);   // ★ 매 명중마다 생성/파괴 → GC
    // ... 재생 후 Destroy ...
}

피격 이펙트 부재의 원인은 코드 누락이 아니라 두 가지다: (1) 가시성 — 파티클이 적 스케일 대비 작고 배경에 묻힘, (2) 구조 — SpawnOneShot 이 풀링 없이 Instantiate/Destroy 를 반복해 빈번한 명중 시 GC 부담. 후자를 제대로 풀려면 공용 풀링이, 풀링이 프리팹을 강참조 집중 보유하지 않으려면 Addressables 약한참조가 전제된다.

초기 진단 보정: SweeperEnemyVisual 의 emission 흰색 번쩍임 제거(커밋 c7ecf502)는 "미완성 리팩토링"이 아니라 TASK-014 A-2 사용자 요청으로 의도된 제거였다. 실제 명중 VFX 는 투사체 측 SpawnOneShot 경로에 살아 있다.

4. 기획 요구사항 (사용자 확정)

  • 지금 공용 풀링 시스템을 신설한다 (임시방편 1개 재사용 대신).
  • MonoBehaviour · POCO 둘 다 풀링 가능한 IPoolable 을 둔다.
  • 활성/비활성 개념을 갖는 객체를 위한 IActivatable 을 분리한다.
  • 풀링 대상은 반드시 IPoolable. 각 구체 타입 → 프리팹 매칭 Repository. Pull() 시 인스턴스화해 반환.
  • 풀링 객체에 전용 인터페이스 + Dispose 강제. (IPooledObject : IDisposable, Dispose = 풀 반환)
  • 생성 분기: MonoBehaviour = Repository 인스턴스화, POCO = 자체 생성자 (Creator 캡슐화로 표현).
  • 기존 IPoolable(14곳) 흡수·전면 교체.
  • 풀 보유 = GameContext DI 주입. 프리팹 참조 = Addressables 약한참조(Repository 강참조 집중 금지) → Addressables 선행.
  • 가독성·공통 로직 묶기·유연성 최우선.

5. 설계 원칙 — 컨벤션 정렬

프로젝트 내 두 풀링 레퍼런스에서 공통 사상을 추출해 통일감을 확보한다.

레퍼런스위치차용 포인트
EnemySpawner 자체 풀 EnemySpawner.cs:39, L247-286 프리팹 키 풀 + 데이터 에셋 분산 참조 — 프리팹은 EnemyData.prefab 이 보유, 풀은 키로만 사용. Repository 집중 강참조를 피하는 근거.
AbilityEffect 풀링 seam AbilityEffect.cs:11-30 Release 위임 + 교체 가능 심 — Release() 가 직접 Destroy 가 아닌 spawner 위임. 구현 교체에 소비자 코드 불변(개방-폐쇄). Creator/Dispose 위임의 선례.
결합 결론: "프리팹 참조는 분산·약하게(EnemySpawner)" + "생성/반환은 위임으로 캡슐화(AbilityEffect)" → Repository 는 타입↔Creator 만 알고, 프리팹 실체는 Addressables 약한참조로 Creator 뒤에 둔다.

레퍼런스 ① EnemySpawner — 프리팹 키 풀

Assets/Scripts/Systems/Enemy/EnemySpawner.cs · L247-266
private MonsterActor GetFromPool(EnemyData data)
{
    if (!pools.TryGetValue(data.prefab, out var queue))   // ★ 프리팹은 데이터가 보유
    { queue = new Queue<MonsterActor>(); pools[data.prefab] = queue; }
    // ... Dequeue 또는 Instantiate(data.prefab) ...
    actor.OnSpawn();
    return actor;
}

프리팹을 풀 한 곳이 강하게 들지 않고 데이터 에셋이 분산 보유한다 — 이를 Addressables 약한참조로 한 단계 더 약화한다.

레퍼런스 ② AbilityEffect — Release 위임 심

Assets/Scripts/Systems/Abilities/Effects/AbilityEffect.cs · L19-23
protected void Release()
{
    if (spawner != null) spawner.Release(this);   // ★ 직접 Destroy 아닌 위임
    else Destroy(gameObject);
}

반환을 호출자/구현에 위임하는 선례. 본 설계의 IPooledObject.Dispose() = 풀 반환으로 일반화한다.

6. 해결 방안 — 변경 사항 (현재 → 목표)

(1) 인터페이스 계층 — 관심사 3분리 신규

Assets/Scripts/Core/Interfaces/IPoolable.cs (확장)
▼ BEFORE (현재)
// 단일 인터페이스, MonoBehaviour 전용 ObjectPool<T> 만 사용
public interface IPoolable
{
    void OnSpawn();
    void OnDespawn();
}
▼ AFTER (목표)
public interface IPoolable           // 풀 생명주기 훅 (시그니처 유지 → 14곳 본문 무변경)
{
    void OnSpawn();
    void OnDespawn();
}
public interface IActivatable        // 활성/비활성 추상 (MB=SetActive, POCO=플래그)
{ bool IsActive { get; } void SetActive(bool active); }
public interface IPooledObject : System.IDisposable { }   // Dispose = 풀 반환

(2) 생성 — Creator 캡슐화 신규

Assets/Scripts/Core/Pooling/IPoolCreator.cs (신규)
▼ AFTER (목표)
public interface IPoolCreator<T> where T : IPoolable { T Create(); }

// MonoBehaviour → Addressables 로 로드한 프리팹 Instantiate
public sealed class PrefabCreator<T> : IPoolCreator<T> where T : MonoBehaviour, IPoolable { ... }
// POCO → 자체 생성자
public sealed class PocoCreator<T> : IPoolCreator<T> where T : class, IPoolable, new() { ... }
  • 풀은 creator.Create() 만 호출 — MB/POCO 분기를 모름.
  • 사용자가 상상한 "MB면 레포 인스턴스화, 아니면 생성자" 분기가 풀 안 if 가 아니라 Creator 주입으로 표현됨(개방-폐쇄).

(3) Repository / Pool / 진입점 신규

Assets/Scripts/Core/Pooling/PoolRepository.cs, Pool.cs (신규)
▼ AFTER (목표)
PoolRepository : 타입 → Creator + 풀 매핑·보유 (프리팹 강참조/SerializeField 금지)
Pool<T>        : Queue<T> + Creator 주입. Get / Return
using var hit = repo.Pull<HitVfx>();   // Get → OnSpawn → SetActive(true)
hit.Play(at);                          // 스코프 이탈 → Dispose() → 풀 반환
Pull<T>() 이 사용자가 말한 "IPoolable.Pull()" 의 실체 — 인스턴스 메서드가 아닌 Repository 진입점. 프리팹 약한참조(Addressables)로 첫 로드 시 UniTask<T> 비동기가 됨.

(4) 피격 VFX 적용 — 첫 소비자 교체

▼ BEFORE

// ... 수명 뒤 Destroy ...                          // 매번 파괴 → GC
