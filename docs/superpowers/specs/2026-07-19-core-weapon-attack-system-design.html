CoreWeapon 공격 체계 설계

설계서 설계 확정 · 구현 전 2026-07-19 · 아레나 코어 공격 주기·발사 묶음 체계

1. 제보 요지

플레이 루프 완성도 감사(TASK-020)에서 확정된 결함이다. 아리스의 투사체 공격이 설계치의 약 1/7 속도로만 나가고, 투사체 능력을 여러 개 모아도 화력이 늘지 않는다.

핵심 원인 한 줄: 연출(공격 모션)이 게임 규칙(발사)을 지배하고 있다. 애니메이션 클립 길이와 전역 시전 채널 1개가 화력을 결정한다.

2. 현재 동작 (재현 경로)

  1. 능력이 쿨다운을 다 채우고 발사를 시도 — ActiveAbilityData.cs:27
  2. 시전 채널에 요청 — ActiveAbilityData.cs:32 RequestCast
  3. 채널이 이미 점유 중이면 거부 — CoreAbilitySystem.cs:115 castReceiver.IsCasting
  4. 거부 시 return하여 ActiveAbilityData.cs:38 ResetCooldown에 도달하지 못함
  5. 채널은 클립 길이만큼 점유 — ArisTowerVisual.cs:115 castRemaining = clip.length (2.667초)
  6. 결과: 실발사 주기 ≈ 2.67초. 투사체 3종이 같은 채널을 나눠 쓰므로 총 발사 수는 1종일 때와 동일

4. 기획 요구사항

사용자 확정 결정

#결정근거
D1능력을 타이밍 축 하나로만 분류 (Main / Sub / Auto)"무엇이 나가는가"를 축에 섞으면 범위 장판형 주공격 캐릭터가 들어올 자리가 없어짐
D2발사 주기는 CoreWeapon이 단독 소유공격 속도를 고칠 때 볼 곳이 항상 한 곳
D3서브는 메인과 한 묶음으로 동시 발사총에 총신을 더하는 체감. 쌓을수록 한 발이 무겁고 느려짐
D4메인은 1개만 보유, 새 메인 획득 시 교체계보 정점에서 "주 무기가 바뀐다"는 강한 체감
D5모션 재생 속도를 발사 주기에 자동 동기화주기라는 숫자 하나가 발사와 연출을 동시에 결정
D6타워 기본 공격 속도는 TowerData에 배치타워 능력치 데이터가 제자리
D7형태가 겹치는 로직은 상속이 아니라 공용 조각 호출상속으로 묶으면 다시 형태가 축이 됨

5. 설계 원칙 — 컨벤션 정렬

새 패턴을 발명하지 않고, 원작의 밸런스 전제와 프로젝트 내 기존 선례에 맞춘다.

레퍼런스위치차용 포인트
원작 — 능력 완전 독립 발사 dot-defense/index.html:22726 모든 능력이 각자 자기 쿨다운만 보고 발사. 서로를 모른다. 발사를 막는 개념이 없다
프로젝트 — 순수 클래스가 규칙을 단독 소유 FusionSystem.cs:23-46 MonoBehaviour가 아닌 순수 클래스로 합성 규칙 전체를 소유. 테스트 가능하고 수정 원천이 하나
결합 결론: CoreWeapon은 원작의 "독립 발사" 전제를 복원하되, FusionSystem과 같은 순수 클래스로 만들어 주기 계산을 EditMode 테스트로 검증한다. 두 선례 모두 이미 프로젝트가 채택한 방식이다.

레퍼런스 A — 원작의 독립 발사

Assets/Reference/dot-defense-main/index.html:22726, 12454
for (const ab of state.tower.abilities) {   // 모든 능력을 매 프레임 순회
  const def = ABILITY_DEFS[ab.id];
  def.tick(ab);                            // 각자 독립적으로 발사
}

// 각 능력의 tick 내부
if (ab.cooldown > 0) { ab.cooldown--; return; }   // 자기 쿨만 본다

원작 캐릭터는 정지 이미지 한 장이라(index.html:23710 drawTower()) 발사 모션 개념 자체가 없다. isCasting·recoil·attackAnim 검색 결과 0건. 본 병목은 아리스 3D 모델 도입 시 우리가 추가한 구조다.

6. 해결 방안 — 변경 사항

6-1. 능력 타입 계층 신설

계층은 "언제 발동하는가" 한 축만 갖는다. 무엇이 나가는지는 구현체가 정한다.

AbilityData
├── ActiveAbilityData (추상)
│   ├── MainAbilityData (추상)   주기의 주인. 공격 모션 보유
│   ├── SubAbilityData  (추상)   메인 발사에 동반. 주기 가감값 보유
│   └── AutoAbilityData (추상)   주기와 무관. 자기 쿨다운으로 동작
└── PassiveAbilityData (추상)
능력타입나가는 것
샷MainAbilityData투사체
범위 마법진 (미래 캐릭터)MainAbilityData바닥 장판
레일건 · 폭풍낙인SubAbilityData투사체
오비탈 · 회오리AutoAbilityData궤도 위성
범위파동 · 기절폭탄 · 계보 결과 3종AutoAbilityData범위 파동
범위 마법진 캐릭터는 MainAbilityData를 상속해 Fire()에서 장판을 깔면 된다. CoreWeapon은 무엇이 나가는지 모르며 코드 변경이 없다.

6-2. ActiveAbilityData — 시전 분기 제거 수정 필요

발사 판단이 CoreWeapon으로 이동하므로, 능력은 "쏘라면 쏜다"만 남는다.

Assets/Scripts/Systems/Abilities/ActiveAbilityData.cs:25-39
▼ BEFORE
public virtual void Tick(in AbilityContext ctx, AbilityInstance self, float deltaTime)
{
    if (!TickCooldown(self, deltaTime)) return;
    ITargetable target = ctx.Finder != null ? ctx.Finder.FindNearest(ctx.Origin, Range) : null;
    if (target == null) return;
    if (castAnimation != null && ctx.Cast != null)
    {
        if (!ctx.Cast.RequestCast(this, self, target, castAnimation)) return;
    }
    else
    {
        Fire(ctx, self, target);
    }
    ResetCooldown(self, ctx);
}
▼ AFTER
// MainAbilityData / SubAbilityData — 스스로 주기를 관리하지 않는다
// CoreWeapon 이 발사 프레임에 Fire 를 직접 호출한다
protected abstract void Fire(in AbilityContext ctx, AbilityInstance self, ITargetable target);

// AutoAbilityData — 자기 쿨다운으로 자율 동작 (기존 방식 유지)
public override void Tick(in AbilityContext ctx, AbilityInstance self, float deltaTime)
{
    if (!TickCooldown(self, deltaTime)) return;
    ITargetable target = ctx.Finder != null ? ctx.Finder.FindNearest(ctx.Origin, Range) : null;
    if (target == null) return;
    Fire(ctx, self, target);
    ResetCooldown(self, ctx);
}

6-3. 발사 주기 계산 신설

기본 주기 = 1 ÷ TowerData.attackSpeed
발사 주기 = 기본 주기 + 메인 가감 + Σ(서브 가감) − 쿨다운 감소 보정
하한      = 0.05초

TowerData.attackSpeed는 이미 존재하는 필드이나 아레나에서 배선이 끊겨 있다 — ArenaModeBootstrap.cs:92-93이 TowerBehaviorTree를 Destroy하여 CombatLogic이 구동되지 않는다. 이를 되살려 쓴다.

진행보유발사 주기한 번에 나가는 것모션 속도
시작샷1.0초샷2.7배
레일건(+0.5)샷 · 레일건1.5초샷 + 레일건1.8배
폭풍낙인(+0.2)셋1.7초셋 다1.6배
오비탈 획득위 + 오비탈1.7초 (불변)셋 다1.6배
부가를 쌓을수록 주기가 늘어나 모션이 오히려 자연스러워진다. 쿨다운 감소 보정은 현재 생산자가 없어 항상 0인 AbilityModifiers.cooldownReduction이 들어올 자리이며, 연결 지점을 이 한 곳으로 고정한다.

8. 검증 시나리오

#시나리오기대자동화
1메인만 장착, 가감 0주기 = 기본 주기가능
2서브 2개(+0.5, +0.2)주기 = 기본 + 0.7가능
3가감 합이 음수로 커짐주기 = 0.05초 (하한)가능
4cooldownReduction 0.2주기에서 0.2 차감가능
5새 메인 장착기존 메인 제거, 서브 유지가능
6AutoAbilityData N개 장착주기 불변가능
7FireAll 1회 호출메인 1회 + 각 서브 1회 발사가능
8타겟 없음 상태로 Tick주기를 소모하지 않고 준비 유지가능
9서브 획득 전후 모션 관찰주기가 늘면 모션이 느려짐수동
10투사체 3종 보유한 모션에 3발이 함께 나감수동

11. 후속 (별도 스펙)

라운드 이어가기 + 적 체력 스케일링 — 원작 기준 라운드당 적 수 고정·체력 지수 증가(3 × 1.35^(n−1)). 현재 총 스폰 80 = 수용 한계 80이라 패배 도달이 불가능한 문제(TASK-020 §3-1)를 해결한다.

만들기는 따로, 확인은 같이. 화력이 정상화되지 않은 상태에서 체력 곡선을 넣으면 몇 라운드 만에 무너지고, 체력 곡선이 없으면 패배가 불가능해 "제대로 됐는지" 판단할 기준이 없다.
