이펙트 예열·발동 견고성 설계

설계 제안서 개선1 TryGet 방식 재확정 이펙트 풀링 마이그레이션 후속 · 2026-07-05

1. 제보 요지

마이그레이션(Task 3~5) 이후, 코드리뷰·사용자 검토에서 ① 실패 처리(발동 실패가 게임 전체로 번짐), ② 로드 효율(예열 순차 로드), ③ 함수 책임 분리("예열 AND 장착" 복합 함수) 지적이 나왔다.

핵심 방향: 실패를 삼키지 말고, try·예외 없이 값으로 다뤄 그 지점만 우아하게 넘긴다. 한 함수는 한 가지만 한다.

2. 현재 동작 (재현 경로)

  1. 능력 발동: AbilityRunner.Tick():44 → 각 active.Tick() → 쿨다운 시 Fire
  2. PooledEffectSpawner.Spawn():17 → PoolManager.Get<T>():64 에서 미예열·컴포넌트 누락 시 예외를 던진다
  3. 예외가 발동 루프로 전파 → 그 프레임 처리를 끊음
  4. 예열: PoolManager.WarmupAsync():34 가 foreach await 로 에셋을 하나씩 순차 로드
발동 실패는 정상 배선·정상 흐름에선 발생하지 않는다(PlayMode 60초 검증 에러 0). 현재는 예외를 던지지만, 이를 예외 대신 반환값(false) 으로 다뤄 해당 발동만 스킵한다.

3. 근본 원인

Assets/Scripts/Core/Pooling/PoolManager.cs · Get<T>() (현재)
public T Get<T>(AssetReference reference, object owner = null)
{
    if (!pools.TryGetValue(reference.RuntimeKey, out Pool pool)) throw ...;  // 예외
    GameObject instance = pool.Get();
    T item = instance.GetComponent<T>();
    if (item == null) { pool.Return(instance); throw ...; }  // 예외
    ...
}

Get 이 실패를 예외로 알린다. 예외를 게임이 죽지 않게 다루려면 어딘가 try-catch 가 필요해지는데, 사용자 결정은 try·예외 둘 다 지양이다. 해법은 실패를 반환값(bool) 으로 바꾸는 것.

4. 기획 요구사항 (사용자 확정)

  • 개선 1 = TryGet 패턴 — try·예외 없이 실패를 값(bool)으로. C# 표준(Dictionary.TryGetValue) 관용구
  • 한 능력 스폰 실패 = 그 발동만 스킵, 다른 능력·게임 정상
  • 개선 2 = 병렬 로드 — 현 규모 실익은 작으나(초기 단계 그룹 1개), 확장 대비 골격 확립
  • 개선 3 = 복합 함수 분리 — "AndB" 금지 컨벤션. 동작 분리, 조율은 호출부

5. 설계 원칙 — 컨벤션 정렬

6. 해결 방안 — 변경 사항

(1) 발동 실패의 우아한 스킵 — TryGet 패턴 수정 필요

    ...

▼ AFTER
// PoolManager — 실패를 bool 로 (try·예외 없음)
public bool TryGet<T>(AssetReference reference, out T item, object owner = null)
{
    item = null;
    if (!pools.TryGetValue(reference.RuntimeKey, out Pool pool))
    {   Debug.LogWarning($"예열 안 됨: {reference.RuntimeKey}"); return false; }
    GameObject instance = pool.Get();
    item = instance.GetComponent<T>();
    if (item == null)
    {   pool.Return(instance); Debug.LogWarning($"{typeof(T).Name} 없음"); return false; }
    Retain(item, pool, owner);
    return true;
}

// PooledEffectSpawner — 실패를 값으로 전달
public T Spawn<T>(AssetReferenceGameObject asset)
{
    if (!pool.TryGet<T>(asset, out T fx)) return null;   // 실패 시 null
    fx.Bind(this); return fx;
}

// 각 능력 Fire/OnEquip — 그 발동만 무산 (try 없음)
ProjectileEffect fx = ctx.Effects.Spawn<ProjectileEffect>(projectileAsset);
if (fx == null) return;   // 스폰 실패 시 이 발동만 스킵
fx.Activate(...);

핵심 변경 포인트

  • try·예외 없이 실패를 bool 로 — AbilityRunner 는 변경 없음(예외가 안 남)
  • 한 능력 스폰 실패 = 그 발동만 스킵, 다른 능력·게임 정상
  • Task 5-A의 Get<T> 예외 가드는 TryGet 의 false + 로그 로 흡수

(2) PoolManager.WarmupAsync — 병렬 예열 로드 수정 필요

Assets/Scripts/Core/Pooling/PoolManager.cs · WarmupAsync()
▼ BEFORE
    foreach (AssetReferenceGameObject asset in assets)
        await WarmupOneAsync(asset, count);   // 순차: A 완료 후 B 시작
▼ AFTER
    using (UnityEngine.Pool.HashSetPool<object>.Get(out HashSet<object> seen))
    using (UnityEngine.Pool.ListPool<UniTask>.Get(out List<UniTask> tasks))
    {
        foreach (AssetReferenceGameObject asset in assets)
        {
            object key = asset.RuntimeKey;
            if (pools.ContainsKey(key) || !seen.Add(key)) continue;  // 예열됨 or 중복
            tasks.Add(WarmupOneAsync(asset, count));
        }
        await UniTask.WhenAll(tasks);   // 병렬
    }
근거(judge): 프리팹별 Pool 생성이 필요해 WhenAll 채택. 실익: 현재 로컬 그룹 1개라 작으나, 그룹 분리·원격 확장 시 커짐 → 초기 골격 확립.
