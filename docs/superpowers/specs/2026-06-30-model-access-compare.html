모델 접근 설계 비교 — 홀드 선언부부터 UI 사용처까지

A) constructor-DI B) 싱글톤 컨텍스트 전 구간 대조 · 2026-06-30
두 방안의 차이는 '모델을 어디에 두고 어떻게 닿느냐' 단 하나입니다. 자동 배선(View 순수 · Presenter 가 View 를 앎 · 팩토리가 Presenter 를 리플렉션 스캔 · UIRoot 는 List<UIView>)은 두 방안 공통입니다. 그래서 아래는 모델 접근 경로만 좌우로 비교합니다.

0. 한눈 요약

A) constructor-DI

GameManager 가 모델을 보유하고, 필요한 곳에 생성자로 전달한다. Presenter 는 받은 모델만 안다.

B) 싱글톤 컨텍스트

GameContext(전역 1개)가 모델을 보유하고, 누구나 GameContext.Instance 로 직접 접근한다. 전달이 없다.

1. 모델 홀드 (선언부)

A) GameManager 인스턴스 멤버 — 전역 진입점 없음
// 합성 루트가 인스턴스 멤버로 보유
public class GameManager : MonoBehaviour
{
    public EconomyModel Economy { get; private set; }
    public WaveModel    Wave    { get; private set; }
    public ScoreModel   Score   { get; private set; }
    // … Core / RoundTimer / Flow / Level
}
B) GameContext 싱글톤 — 전역 진입점 1개
// 전역에서 접근 가능한 단일 컨텍스트가 보유
public sealed class GameContext
{
    public static GameContext Instance { get; private set; }   // 전역 진입점

    public EconomyModel Economy { get; private set; }
    public WaveModel    Wave    { get; private set; }
    public ScoreModel   Score   { get; private set; }
    // … Core / RoundTimer / Flow / Level
}
차이: B 는 static Instance 한 줄이 핵심. 이 한 줄이 "어디서나 접근"을 만들고 동시에 "전역 가변 상태"를 만든다.

2. 모델 생성·초기화

A) GameManager.Awake 에서 생성
private void Awake()
{
    Economy = new EconomyModel();
    Wave    = new WaveModel();
    // …
    Economy.Initialize(startGold);
}
B) GameManager.Awake 에서 GameContext 구성
private void Awake()
{
    GameContext.Create(startGold);   // 컨텍스트가 모델을 생성·보유
}

// GameContext 내부
public static void Create(int startGold)
{
    Instance = new GameContext();
    Instance.Economy = new EconomyModel();
    Instance.Wave    = new WaveModel();
    Instance.Economy.Initialize(startGold);
}

3. Presenter 로 전달

A) UIContext 로 묶어 팩토리에 주입 (전달 있음)
// GameManager.Start
var ctx = new UIContext(Economy, Score, Wave, Timer, Flow, Level, capacity);
var factory = new UIPresenterFactory(ctx);
uiRoot.Inject(factory);
B) 전달 없음 (Presenter 가 전역에서 직접 가져감)
// GameManager.Start
var factory = new UIPresenterFactory();   // 모델 주입 안 함
uiRoot.Inject(factory);
B 의 이득이 가장 큰 지점: 전달 보일러플레이트(UIContext 구성·주입)가 통째로 사라진다.

4. Presenter 의 모델 접근 (사용처 핵심)

A) 생성자에서 받은 모델을 필드로 — 의존성이 시그니처에 드러남
public sealed class ArenaHudPresenter : UIPresenter<ArenaHudView>
{
    private readonly EconomyModel economy;
    private readonly ScoreModel   score;

    public ArenaHudPresenter(ArenaHudView view, UIContext ctx) : base(view)   // 뭘 쓰는지 보임
    {
        economy = ctx.Economy;
        score   = ctx.Score;
    }

    protected override void OnInitialize()
    {
        Bind(economy.Gold, view.ApplyGold);
        Bind(score.Score,  view.ApplyScore);
    }
}
B) Instance 에서 직접 — 생성자 짧음, 의존성은 메서드 안에 숨음
public sealed class ArenaHudPresenter : UIPresenter<ArenaHudView>
{
    public ArenaHudPresenter(ArenaHudView view) : base(view) { }   // view 하나뿐

    protected override void OnInitialize()
    {
        var ctx = GameContext.Instance;
        Bind(ctx.Economy.Gold, view.ApplyGold);
        Bind(ctx.Score.Score,  view.ApplyScore);
    }
}
A: 생성자가 길지만 "이 Presenter 는 Economy·Score 가 필요"가 한눈에.
B: 생성자가 짧지만 의존성은 OnInitialize 안의 Instance 접근에 흩어져 "숨은 의존성"이 됨.

5. 팩토리 (자동 배선 — 공통 구조, 인자만 차이)

두 방안 모두 Presenter 를 리플렉션 스캔해 TView → Presenter 매핑을 자동 구축합니다(지적 반영: View 는 Presenter 를 모름). 차이는 생성 시 ctx 를 넘기느냐뿐입니다.

A) 팩토리가 ctx 보유, 생성 시 (view, ctx)
public sealed class UIPresenterFactory
{
    private readonly UIContext ctx;
    public UIPresenterFactory(UIContext ctx) { this.ctx = ctx; }

    public IPresenter Create(UIView view) =>
        (IPresenter)Activator.CreateInstance(MapToPresenter(view), view, ctx);
}
B) 팩토리 의존성 0, 생성 시 (view) 만
public sealed class UIPresenterFactory
{
    public IPresenter Create(UIView view) =>
        (IPresenter)Activator.CreateInstance(MapToPresenter(view), view);
}
MapToPresenter = 어셈블리에서 UIPresenter<TView> 구현들을 스캔해 만든 Dictionary<ViewType, PresenterType> (두 방안 동일).

6. UIRoot (공통 — 거의 동일)

// 두 방안 동일: 리스트 순회 → 생성 → Initialize
[SerializeField] private List<UIView> views;

public void Inject(UIPresenterFactory factory)
{
    foreach (UIView view in views)
    {
        IPresenter p = factory.Create(view);
        if (p == null) continue;
        presenters.Add(p); p.Initialize();
    }
}
유일한 차이: A 는 Inject(factory) 의 factory 가 ctx 를 들고 있고, B 는 빈 factory. UIRoot 코드 자체는 같다.

7. 새 모델 / 새 UI 추가 시 수정 지점

새 모델 QuestModel 을 추가하고 새 패널에서 쓸 때

단계A) constructor-DIB) 싱글톤 컨텍스트
모델 보유처GameManager 에 프로퍼티 1줄GameContext 에 프로퍼티 1줄
생성GameManager.Awake 1줄GameContext.Create 1줄

핵심: '새 모델 = 보유처 한 곳에 1줄'은 A·B 모두 동일(A 는 GameManager, B 는 GameContext). B 가 줄이는 건 UIContext 전달 객체 수정뿐이다. '컨텍스트를 매번 수정해야 한다'는 우려는 B 로 가도 GameContext 수정으로 남는다 — 다만 전달부가 없어 손대는 곳이 1곳 적다.

8. 테스트

A) 가짜 모델을 생성자로 주입 — 고립 테스트
var fakeEconomy = new EconomyModel();
fakeEconomy.Initialize(100);
var ctx = new UIContext(fakeEconomy, /* … */);
var presenter = new ArenaHudPresenter(view, ctx);   // 전역 없이 격리
B) 전역 Instance 를 먼저 세팅해야 함
GameContext.Create(100);                 // 테스트마다 전역 준비·정리 필요
var presenter = new ArenaHudPresenter(view);
// 테스트 종료 시 Instance 리셋 안 하면 다른 테스트로 오염
모델 자체의 단위테스트(new EconomyModel())는 두 방안 모두 영향 없음. 차이는 Presenter 단위테스트에서만 난다(B 는 전역 세팅·정리 부담).
