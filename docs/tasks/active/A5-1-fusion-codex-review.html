3. reconcile 결과 (프로젝트 제약·컨벤션 대조)

Codex 제안을 HARD 제약·CLAUDE.md 컨벤션·실사용 위험도로 판정했다. HARD 위반은 0건이며, 대부분 유효하나 재설계가 필요해 후속 TASK로 분류한다.

#판정근거 / 실제 위험
H1Accept · 재설계유효. 단 Fuse는 재료 2개를 먼저 제거하므로 슬롯 여유가 생겨 AddAbility 실패 가능성은 실사용상 낮음. 원자적 커맨드(성공 반환)로 묶는 개선은 후속.
H2Accept · 재설계구조적으로 타당. 실사용 위험은 낮음 — 선택 즉시 current=null로 재클릭 차단, 선택 중 timeScale=0이라 로드아웃 불변. 결과 능력은 AbilityData 식별자로 재해석하는 편이 견고.
H3Defer · 사용자 판단가장 가치 있는 장기 제안. CardOfferService/FusionCatalog 경계 도입은 실제 리팩토링 규모라 승인 필요.
M1DeferH3와 한 묶음(경계 신설 시 자연 해소).
M2Accept · 후속다단 계보 도입 시 필수. 지금은 단일단계 데모라 YAGNI — 검증된 불변 그래프/인덱스를 부트스트랩에서 구축하는 안을 다단 구현 TASK에 반영.
M3Defer레시피 1·풀 7로 규모 미미, 생성은 레벨업 시에만 발생 → 조기 최적화. 단 CollectionPool 컨벤션 정렬 여지는 인정.
M4Accept · 재설계H1/H2와 동일 계열 — 원자적 fuse 커맨드로 함께 해소.
Codex 질문 답변: ① 예열 중 입력은 current=null로 차단됨(이중적용 안전). ② RemoveAbility의 슬롯 해제·실패보고 동기성은 IAbilityCommandTarget 구현 확인 필요(원자성 개선 시 함께 점검).

5. 잔여 작업 / 커밋 가능 여부

  • 현재 구현은 커밋 가능 — HARD 위반 0건, EditMode 619/619 통과, 인게임 합성 라이브 검증 완료. Codex 지적은 전부 개선·확장 방향이지 현 기능을 막는 결함이 아님.
  • 후속 TASK 후보: (A) 원자적 fuse 커맨드 + 재검증(H1·H2·M4) → 다단/비정지 도입 전 우선. (B) 카드 도메인 경계 CardOfferService(H3·M1) → 카드 종류 확장 시. (C) 다단 계보 검증 그래프(M2) → 기존 TASK-017(계보 비주얼 에디터)와 함께 다룰 영역.
  • 즉시 적용 안 함: 사용자가 "피드백 요청"만 했고, 세 항목 모두 재설계/규모가 있어 승인 후 진행.
권장 순서: 지금 커밋(기능 확정) → (A) 원자 커맨드 소규모 정리 → 다단 계보 착수 시 (B)(C). (A)만 선행하면 다단 확장이 안전해진다.
